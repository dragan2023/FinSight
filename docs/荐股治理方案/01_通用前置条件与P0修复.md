## P0-1 修正概率基率的复权口径（唯一正确性缺陷）

### 问题

顾问的情景概率与仓位建议建立在一条"历史状态基率"上，而这条基率用**未复权收盘价**计算。

### 证据链

1. 本地仓库 `daily_k` 的 `adjusted` 列**唯一取值是 `none`**（1026 万行全部未复权）。
2. `market_warehouse/repository.py:194-197` 的 `history()` 直接取 `close_price`，不做复权。
3. `advisor/graph.py:617-624` **优先**用仓库数据；只有 `len(rows) < 81` 时才回退到
   `fetch_price_history()`（其 `DEFAULT_HISTORY_ADJUST="forward"`，即前复权）。
4. `advisor/algorithms/base_rate.py:65-66` 用该序列算前瞻收益：
   `returns_20.append(closes[index + 20] / closes[index] - 1)`。
5. 该基率经 `graph.py:640-708 _enrich_card()` 进入 `calculate_scenario_ev()` 与
   `calculate_volatility_target()` / `calculate_half_kelly()`。

**后果**：除权除息日股价机械性下跌被计入真实负收益。普通分红影响小，但 A 股高送转
（如 10 送 10 导致价格腰斩）会严重污染基率，进而同时污染概率分布与仓位建议。

**反常之处**：仓库同步得越完整，走的越是这条有偏路径；仓库为空反而得到无偏结果。

### 修法

优先复用仓库中**已有的**公司行动感知序列，不要新写一套：

- `market_warehouse/repository.py:203+` 的 `corporate_action_total_return_history()`
  已实现"除权日假设持有人收到现金分红、收到送股、并按公告价全额配股"的总收益序列。
- 该函数 docstring 明确警告：原始导出**没有公告时间戳**，可能包含**已计划的未来除权日**，
  因此只可用于结算与回溯，**不得作为前瞻信号输入**。
- 因此修法是：为基率构造一条"**as-of 截断**的复权收益序列"——只使用
  `ex_date_ms <= 评估日` 的事件。这既修正了复权口径，又不会引入未来信息。

同时必须**在证据文本中显式标注口径**（例如 `basis: corporate_action_total_return_v1`），
因为 `base_rate.py` 的 `note` 字段目前只提到幸存者偏差，未提及复权口径。

### 验收标准

1. **合成用例**：构造含一次 10 送 10 事件的日 K，断言除权日不产生机械性负收益，
   且 20 日前瞻收益分布与"无事件对照序列"一致（容差内）。
2. **真实用例**：取一只历史上发生过高送转的已确认标的，对比修复前后基率中位收益，
   差异必须可归因于该公司行动。
3. **无未来信息**：断言评估日为 T 时，序列中不存在 `ex_date_ms > T` 的事件被应用。
4. 新增回归测试纳入 P0-2 的测试网。

### 工作量

约 10–30 行有效改动 + 2 个测试。**这是全套方案里投入产出比最高的一项。**

## P0-3 打通候选池数据通路

### 问题

全仓库**没有选股模块**。每日候选靠人工按方案文档 §3.1 手抄"热度前 5 + 成交额前 10"。

`market_warehouse/api/` 的 `query` 端点只支持三个固定指标：

```python
metric: Literal["breadth", "liquidity", "sample"]   # api/market_warehouse.py:16
```

### 原料评估（够用）

| 原料 | 规模 | 用途 |
|---|---|---|
| `daily_k` | 1026 万行 / 5556 只 / 2427 交易日 / 2016-09-06→2026-09-04 | 流动性、量价、动量、波动 |
| `financial_statements` | 131.6 万行 / 5556 只 / 26 字段 / 10 个年报期 | 年报口径适合 F-Score/Z-Score，**但字段不足以算出这两个指标**（见下方缺口） |
| `adjustment_factors` | 5.71 万行 / 5420 只 / 1991→2026 | 复权与总收益序列 |

#### 财务因子当前的字段缺口（必须在本项内解决）

`advisor/algorithms/` 里 F-Score 与 Z-Score 的公式**已经写好**，但用**纯本地仓库数据算不出来**：

| 指标 | 实现 | 所需字段 | 在 `financial_statements` 的 26 字段中 |
|---|---|---|---|
| Piotroski F-Score | `f_score.py` | `total_assets_net_ratio`(ROA)、`act_cash_flow_net`、`assets_total`、`listed_days`、`is_st` | ROA **不在**（它属 financial *indicators* 端点，见 `field_dictionary.py:108` 的 `PERCENT_INDICATORS`）；`listed_days`/`is_st` 也不在 |
| Altman Z-Score | `zscore.py` | `retained_earnings`、`market_value_equity` 等 5 因子 | 二者**全仓库无人生产**——grep 整个 `backend/`，`retained_earnings` 与 `market_value_equity` **只出现在 `zscore.py` 自身** |

**后果**：

- **Z-Score 在生产中永远处于降级状态。** `_format_z_score()`（`graph.py:1101-1104`）会诚实输出
  "Z 值暂不计算（缺少留存收益、权益市值/负债）"——不崩、不编数，但也**永远不会算出结果**。
- **F-Score 只在顾问链里可用**：`_fundamental_pack()` 会额外调 `fetch_indicators()` 补 ROA；
  一旦走纯本地仓库路径，它也降级。

**这对 C2 的因子层有直接约束**：自动化日更排序必须建立在**本地数据**上（红线要求付费 API
不得后台自动调用），而本地数据当前算不出这两个财务因子。因此本项必须二选一：

- **(a)** 扩展同步范围，把 indicators（`total_assets_net_ratio` 等）与 Z-Score 所需字段一并落库
  （由用户显式触发的同步脚本）；
- **(b)** 先只用**量价与流动性因子**，把财务因子推到后续阶段，并在文档中登记该限制。

### 修法

新增只读的横截面通路，**并严格保持既有约定：禁止任意 SQL**。

1. 在 `market_warehouse/repository.py` 增加**固定 SQL 模板**方法，例如
   `cross_section(date_ms, *, universe, factors, min_turnover, limit)`，
   参数经枚举校验后拼入模板；**绝不接受调用方传入的 SQL 片段或表达式**。
2. 新增因子层（建议 `backend/app/screener/`），负责：
   - 定义因子集合（流动性、动量、波动、F-Score、Z-Score、估值分位）
   - **一律走公司行动感知的复权收益序列**（同 P0-1）
   - **as-of 语义**：任何因子在日期 T 只能使用 `<= T` 的信息
3. 股票池规则必须显式且可复现（对齐文档 §3.1）：排除 ST、停牌、次日无法正常买入的
   连续涨停股、身份无法确认的证券。
4. 输出必须标注为**候选池**（既有红线要求），并携带入池理由与数据日期。

### 验收标准

- 给定 `(交易日, 股票池规则, 因子集, 参数)` 能**确定性复现**同一份排序（含 `params_hash`）。
- 对同一日期重复运行结果完全一致；对历史日期运行不得读取该日期之后的数据（含除权事件）。
- 股票池规模与 `daily_k` 当日实际标数（5548）量级一致，且被排除的标的可解释。
- 输出中每只股票都能回溯到具体因子值与数据来源。

### 工作量

固定模板 + 因子层 3–5 天（C1 只需最小版：1–2 天，仅实现成交额与流动性排序）。

## P0-4 修数据溯源与未来信息泄漏

### 4.1 `financial_statements` 不可复现

| 观测 | 结论 |
|---|---|
| 131.6 万行 / 5556 只 / `income` 62.9万、`balance` 36.9万、`cashflow` 31.8万 | 数据本身完整 |
| 全仓 grep `financial_statements` 仅 4 处命中，**全部是读取/能力名，无 `INSERT`** | 当前代码树无写入者 |
| `market_warehouse/repository.py:13-21` 的 `_connect()` 只建 `daily_k` 与 `adjustment_factors` | 建表语句里也没有它 |
| `scripts/sync_full_market_financials.py:29` 声明的进度日志 `logs/financials_sync_progress.jsonl` **不存在** | 看不出该脚本真实跑过 |
| `period_key` 只有 10 个 `20XX-Q4`，无任何 Q1/Q2/Q3 | 实际只有年报口径，与脚本声明的 `period="quarterly"` 不符 |
| `evidence_id` 全为空串 | 未回链 SQLite 证据账本，与"关键数值必须绑定证据 ID"的承诺有缺口 |

**修法（二选一，必须明确选择并在文档中登记）**：

- **(a) 重建为可复现数据集**：写一个真正写 DuckDB 的同步脚本（现有脚本只写 SQLite
  证据/缓存），记录真实期间语义与 `evidence_id` 回链，并把进度日志纳入正常路径。
- **(b) 冻结为一次性数据集**：在 `schema.py` 与 `market_datasets` 中显式登记其为
  只读历史快照、注明来源不明与口径限制，**禁止任何代码假定它可以增量更新**。

在做出选择前，**任何因子设计都不得假定财务数据会按季刷新**。

### 4.2 `schema_version` 与同步记录漂移

- `market_datasets` 中 `daily_k` / `daily_k_10d` 记为 `market_daily_v1`，而当前代码常量是
  `market_daily_actions_v2`（`market_warehouse/schema.py:1`）；`market_daily_v1` 在现仓库中
  已无任何出现。**数据比代码旧一代。**
- `market_sync_runs` **0 行**，而 `market_datasets` 有 3 行。`_ingest_file()`
  （`market_warehouse/service.py:151-169`）本该同时写两者，正常流程不可能只写前者
  → 这 3 个数据集来源可疑（迁移前灌入 / 手工 / 记录被清理）。

**修法**：重新执行一次完整同步以对齐版本与运行记录；若因数据量不便重跑，则显式登记
这 3 个数据集为 legacy 并说明来源存疑。

### 4.3 未来除权日泄漏（高危）

`adjustment_factors` 的最大除权日 **2026-09-15 晚于最后交易日 2026-09-04**，
即官方导出**包含已公告但尚未发生的除权事件**。任何在信号计算中"顺手 join 复权因子"的
实现都会把未来信息泄漏进历史特征。

**修法**：

1. 在复权/总收益入口统一强制 **as-of 截断**（`ex_date_ms <= 评估日`）。
2. 增加一个**守卫测试**：构造含未来事件的序列，断言在 T 日计算的特征与"截断到 T"的结果一致。
3. 在 `repository.py:203+` 已有 docstring 警告的基础上，把约束提升为代码断言。

### 工作量

4.1 选择 + 落实 1–2 天；4.2 重跑或登记 0.5 天；4.3 截断与守卫测试 0.5 天。

### 剩余项（需要你操作）

1. **云端清除（必须做；我无法完成）**。本机到 GitHub 网络不通（`git ls-remote` 返回
   `Recv failure: Connection was reset`），所以我无法替你 push 或删库。两种做法：
   - **推荐**：在 GitHub 网页**删除该仓库并重建为私有仓库**，再从本机重新推送。
     这是唯一能保证旧对象彻底消失的做法——`--force` 之后未引用的对象仍可能在一段时间内按 SHA 访问。
   - 或：`git push --force origin main`（旧提交变为不可达，但 GitHub 侧可能仍保留一段时间）。

2. **轮换 5 个 API Key（建议做）**。风险不高——密文没有根密钥打不开，而 `.env` 从未进过 git——
   但轮换是唯一能把"已上网的密文"彻底变成无害的办法。做法：去各服务商后台重新生成，
   在设置页重新导入。**同花顺与博查优先**（有额度/付费属性）。

3. **`git gc --prune=now`**。重写历史后大量对象不可达（含一个 183 MB 的旧 DB blob
