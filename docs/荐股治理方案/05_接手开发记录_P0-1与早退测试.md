### 1.2 真实数据上的修正幅度（星宇股份 601799.SH）

只读探针，as-of = 2026-09-13，仓库窗口 2016-09-06 → 2026-09-04（2427 根日 K）：

| | 未复权（旧） | 总收益（新） |
|---|---|---|
| 匹配状态 | `down_low_vol` | **`down_high_vol`** |
| 20 日样本数 | 611 | **491** |
| 20 日中位收益 | **−0.273%** | **+1.695%** |
| 20 日胜率 | **48.28%** | **57.64%** |
| 60 日中位收益 | +2.353% | +7.183% |

**机制（已实测量化，不是推测）**：最新 20 日波动率与动量在两种口径下**完全相同**
（2.1693% / −19.1183%）——因为最近 20 日没有除权日。差异全部来自**历史波动率中位数**：

```
未复权阈値 = 2.1735%   最新波动 2.1693%  →  2.1693 <= 2.1735  →  low_vol
总收益阈值 = 2.1555%   最新波动 2.1693%  →  2.1693 >  2.1555  →  high_vol
                                            ↑ 仅差 0.018 个百分点
```

即：**现金分红的除息缺口把历史波动率中位数抬高了 0.018pp，恰好把当前状态判错档，
于是匹配到完全不同的历史样本**（611 → 491 个观测），中位收益与胜率随之整体漂移。
这不是"加了一点噪声"，而是**换了一个样本**，直接影响 half-Kelly 的胜率与盈亏比输入。

补充事实（推翻"高送转才严重"的直觉）：

- 星宇股份 18 个公司行动事件**全部是现金分红**，`per_share_bonus` 全为 0，**没有一次送转**。
  单次除息机械跌幅只有 −0.15% ~ −1.64%。
- 即便如此，修正后总收益口径的末值与未复权末值之比为 **1.1234**，即旧口径**丢掉了 12.34%
  的累计分红收益**。
- 12 个事件被应用，6 个落在仓库覆盖之前（2011–2016）记为 unmatched，`invalid_factor_count = 0`。

**结论：P0-1 不是"高送转保险"，而是常态正确性修复。** 普通年度分红就足以翻转基率状态档。

### 1.3 未来信息泄漏（F8）实测确认

```
daily_k 最后一根           2026-09-04
adjustment_factors 最大除权日 2026-09-15
ex_date_ms > 最后一根日K 的行数：88
```

`adjustment_factors` 里确实有 **88 行已公告但尚未发生**的未来除权日。因此口径切换
**必须**同时做 as-of 截断，否则修好复权口径反而会引入未来信息。本实现把截断下沉到
两层：仓库 SQL 的 `[start_ms, as_of_ms]` 窗口 + `total_return_closes()` 内的 `as_of_ms` 过滤。

## 2. 早退测试：4 次实验，全部 `insufficient`

对三个"已确认标的"调用 `POST /api/strategy-experiments`（区间 2019-01-01 → 2026-09-13，
单边成本 10bps）。**这些是真实的同花顺前复权数据，不是构造用例。**

| 标的 | 策略 | 日 K | 验证段+测试段交易 | 验证段收益 | 测试段收益 | 测试段超额 | 判定 |
|---|---|---|---|---|---|---|---|
| 601799.SH 星宇股份 | `trend_20_60_v1` | 1868 | 9 + 5 = **14 < 20** | −20.57% | **−5.47%** | +35.39% | `insufficient` |
| 601799.SH 星宇股份 | `reversal_5d_v1` | 1868 | 3 + 1 = **4 < 20** | −2.70% | **−9.05%** | +31.81% | `insufficient` |
| 688836.SH | `trend_20_60_v1` | **18** | 0 + 0 | — | — | — | `insufficient` |
| 688836.SH | `reversal_5d_v1` | **18** | 0 + 0 | — | — | — | `insufficient` |
| 881166.TI | 任意 | — | — | — | — | — | **HTTP 422** |

三个把候选池打掉的硬事实：

1. **`881166.TI`（军工装备）根本提交不了。** 它是 `asset_type = a-share-index` 的指数，
   而 `StrategyExperimentInput.thscode` 的正则是 `^[0-9]{6}\.(SH|SZ|BJ)$` → 422 校验失败。
   三个"已确认标的"里有一个**在数据模型层面就不是可实验对象**。
2. **`688836.SH`（宇树科技-W）只有 13 根日 K**（仓库 2026-08-19 起，接口返回 18 根）。
   新上市标的，`bars >= 500` 的门禁在数年内都不可能满足。
3. **门槛不是"交易笔数"这一个技术细节。** 星宇股份在 6.7 年样本外窗口里
   `trend_20_60_v1` 只有 14 笔、`reversal_5d_v1` 只有 4 笔；**即便笔数够，测试段收益也是负的**
   （−5.47% / −9.05%）。也就是说：**当前单标的固定规则在已确认标的上没有可复现优势**。

另：`strategy_experiments` 表从 **0 行**变为 **4 行**（全部 `insufficient`），
这 4 行是真实落库的实验记录，可用于验证候选门禁的排除路径。

### 2.1 判定（决策 + 理由）

**决策 1：候选池与因子层（C2）从"可选"升级为"前置必需"，但仍不放松任何门禁。**

理由：本次早退测试**没有**证明"门禁太严"，恰恰相反——它证明了门禁在正常工作：

- 门禁是**过滤器**，不是本应给每个标的都放行的闸门。5556 只标的中只有少数应当成为
  候选，这正是设计的意图。真正致命的不是"3 个标的都没过"，而是**能提交给门禁筛选的标的
  只有 3 个，其中 1 个指数提交不了、1 个只有 13 根 K 线**——池子本身不成立。
- 人工手抄候选池在数据层面已被证伪：抄出来的标的可能连实验都跑不起来。

**决策 2：C2 的验收标准增加一条"可筛选标的规模"指标。**

即：每个交易日必须能对**数百只流动性达标的标的**跑完实验批，并报告
"通过 `candidate` 门禁的数量"。若长期为 0，则结论是"当前策略族无效"（合格结论，
按红线不得通过调参或延长观察期来"修复"），而不是"门禁有问题"。
可筛选基础已实测充足：`daily_k` 共 5556 只标的，其中 **5286 只有 ≥500 根日 K**，
仅 270 只不达标。

**决策 3：C2 的实验批必须走本地 DuckDB，不得走 `/api/strategy-experiments`。**

理由：该端点每次调用都要为单只标的发一次 HTTP（同花顺金融数据 API **免费开放、仅限流**，
不是付费服务——权威口径见 `docs/FinSight使用说明书.md:69`；本机付费的只有博查搜索）。
按 5000 只/日跑批要走 5286 次网络请求、受限频约束、且不可确定性复现；按 D6
（自动化只建立在本地 DuckDB 上）批量实验本就不该走这条网络路径。**而 P0-1 正好提供了
这条数据通路**：
`total_return_closes()` 产出的公司行动总收益序列与 `adjust="forward"` 在收益率口径上等价
且同样无未来信息，可直接作为本地实验的数据源。落地时需同步把数据源口径写进
`data_snapshot`（当前固定写 `{"adjust": "forward"}`，走本地源后必须改记为
`corporate_action_total_return_v1`），否则实验落库会谎报数据来源——这条与 P0-1 §1.4
第 5 条测试是同一类"口径必须自证"的要求。

**决策 4：不修改 `strategy/validation.py:grade()` 的任何阈值。** 见 §4.3 的待预注册事项。

### 2.2 这改变了什么排期

`04_接手开发提示词.md` §8 的原排期是"C1 其余（4 张治理表 → 冻结 → 双轨结算 → 落盘）→ C2"。
本次结果**不改变这个顺序**，但改变 C2 的定位与验收：

- C1 余项照做（治理表、程序性冻结、双轨结算、每日落盘）。
- C2 不再是"可选优化"，而是**能否产生候选的唯一天花板**；其验收从"有 `screener/` 目录"
  改为"每日可对数百只标的产出实验批 + 通过门禁数量可审计"。

### 3.4 修复的真实回归：研究链"截断"分类丢失

**症状**：`OutputIntegrity.TRUNCATED` 在生产中**不可达**。

**证据链**（逐条实查）：

1. `research_graph.py:782` 读 `item.get("integrity") == "incomplete"`；
   而全文件**没有任何地方写入** `"incomplete"` 这个字符串 → 该分支恒不成立。
2. 归档版 `_recover_section` 有一条专门的截断分支（写入
   `truncated_no_recovery` / `recovery_model_error` / `truncated_after_recovery`，
   `integrity = "incomplete"`）。V2 把它删掉，改为统一走 `_repair_format`。
3. `_repair_format` 没有截断意识：失败时写 `reason = "repair_failed"`、
   `integrity = "unstructured"`，且 `text = failed_turn.content`（**丢弃恢复输出**）；
   成功时无条件标 `markdown_rewritten`——**即使重写结果是一份通过校验的完整结构化章节**。
4. 这个丢失**不是有意设计**：模块 docstring（第 11–16 行）与归档版逐字相同，仍写着
   「截断恢复：… 该节 incomplete … 自动恢复一次」；`prompts.py:88 recovery_user()`
   与 `st["recovery_used"]` 变成死代码；前端 `frontend/src/api/research.ts:323`
   与 `docs/FinSight使用说明书.md` 仍在展示「存在截断章节」这个**永远不可能出现**的状态。

**修法（改生产，不放宽测试）**，`backend/app/agent/research_graph.py`：

- `_recover_section()` 标记 `st["recovery_used"] = True` 并以 `truncated=True` 进入重写；
- `_repair_format(..., *, truncated=False)`：
  - 截断路径改用**现成但已成死代码的** `recovery_user()` 提示词（它的文本恰好正确描述了
    "输出被截断，已整体作废，不与本次拼接"，而 `format_repair_user` 的
    "未找到完整的 Markdown 标题" 对截断是失实描述）；
  - 恢复失败 → `reason = "truncated_after_recovery"`、`integrity = "incomplete"`、
    `text = turn.content or failed_turn.content`（**保留恢复产物作为证据**）；
  - 预算不足/已修复过 → `reason = "truncated_no_recovery"`、`integrity = "incomplete"`；
  - 截断恢复的占位文案含"截断"二字，使前端可读；
  - **重写结果解析为完整结构化章节时不再标 `markdown_rewritten`**（该标签会把报告降级为
    `partial` 并附上"已按可读正文重新生成"的失实说明；截断只让被丢弃的那一轮作废）；
- 非截断路径（`turn.error`、Markdown 标记损坏）**行为逐字未变**，`repair_failed` /
  `unparseable_no_repair` / `markdown_rewrite_invalid` 三个 reason 保持不变。

**边界说明（诚实披露）**：第 6 项测试我把断言从 `natural_language` 改成 `markdown_rewritten`，
因为 V2 确实把该状态改了名，且 `_integrity` 对两者做同一映射（都 → `PARTIAL`），
行为无差异。这属于"重命名"，不属于放宽。
