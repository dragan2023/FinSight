## 0. 一句话结论

**财务数据已经可以本地、可复现、带时点地取了**，但过程中实测出**一个会让整个 point-in-time
做假的问题**，值得先看：

| 事实 | 实测值 |
|---|---|
| **同花顺三表接口的 `report_date_ms` 不能当披露日用** | 资产负债表 Q1/Q2/Q3 滞后 **25/47/25 天**（正常）；但**资产负债表 Q4 与利润表/现金流量表的全部季度滞后中位数 386–445 天（≈ 整整晚一年）** |
| 三表对**同一报告期**的披露日是否一致 | **90/130 组不一致（69%）** |
| `indicators` 端点有没有披露日 | **没有**（`normalize_indicators` 给 `disclosed_at=None`）→ 它**不能**用于历史 point-in-time |

**处置（D59）**：披露时间有**法定上限**（交易所《股票上市规则》5.2.2：年报 4 个月、半年报
2 个月、一/三季报 1 个月），所以闸门取

```
available_from_ms = min(接口披露日, 法定披露截止日) + 1 天
```

- 接口日期**早于**截止日 → 说明它可信（资产负债表 Q1 的 +25 天就是），采信它，数据更新鲜；
- 接口日期**晚于**截止日 → 说明它漂移了（利润表那批），回落到法定截止日——
  既不白等一年，也**不会比法定截止日更早**，因此不会引入未来信息。

两个日期都落库、并标注 `available_basis` 采信了哪一个（口径自证，与 D12 同一纪律）。

**另一个好消息**：F-Score 的 **7/9 项现在能用三表在本地算出来**（不需要 `indicators`）。
本地比率与厂商指标的交叉校验：**资产负债率、销售毛利率完全一致（相对差 0.00%）**，
ROA 与总资产周转率差 **<1%**（口径差异，见 §4）。

## 1. 实测：披露日为什么不能用

### 1.1 方法

对 5 只标的（`600519.SH` / `000001.SZ` / `300750.SZ` / `601799.SH` / `002415.SZ`）×
3 张报表，用 `MarketService.fetch_statement(period="quarterly")` 取回 **390 条**
(报表, 报告期) 记录，逐条算「披露日 − 报告期末」的滞后天数。

### 1.2 结果：按「报表 × 季度」看

| 报表 × 季度 | n | 滞后中位数（天） | 范围 |
|---|---|---|---|
| 资产负债表 Q1 | 35 | **25** | 15–30 |
| 资产负债表 Q2 | 35 | **47** | 24–59 |
| 资产负债表 Q3 | 30 | **25** | 17–31 |
| 资产负债表 Q4 | 30 | **445** | 206–477 |
| 利润表 Q1 / Q2 / Q3 / Q4 | 35/35/30/30 | **386 / 409 / 388 / 445** | — |
| 现金流量表 Q1 / Q2 / Q3 / Q4 | 35/35/30/30 | **386 / 409 / 388 / 445** | — |

同一批数据里，资产负债表的 Q1–Q3 是**完全正常的**（季报 25 天、半年报 47 天），
而**利润表与现金流量表的每一期都晚了约一年**。

### 1.3 机制：日期像是"后来那次报告"的

`600519.SH` 的实例（节选）：

| 报告期 | 利润表披露日 | 资产负债表披露日 | 期末 | 利润表滞后 |
|---|---|---|---|---|
| 2026-Q2 | 2026-08-15 | 2026-08-15 | 2026-06-30 | 46 |
| 2026-Q1 | 2026-04-25 | 2026-04-25 | 2026-03-31 | 25 |
| 2025-Q4 | 2026-04-17 | 2026-08-15 | 2025-12-31 | 107 |
| 2025-Q3 | 2025-10-30 | 2025-10-30 | 2025-09-30 | 30 |
| 2025-Q2 | **2026-08-15** | 2025-08-13 | 2025-06-30 | **411** |
| 2025-Q1 | **2026-04-25** | 2025-04-30 | 2025-03-31 | **390** |

2025-Q2 的利润表披露日与 **2026-Q2** 的完全相同（2026-08-15）、2025-Q1 与 **2026-Q1** 相同
（2026-04-25）——像是把"最近一次包含该期比较数的报告"的日期填了进来。
逐组检验：**12% 的组合与后一年同季的日期完全相等**（其余是约一年后但不等），
所以更准确的描述是**"日期被推移到了下一个报告周期"**，而不是逐字复制。

> **诚实边界**：以上是**推断的机制**（基于日期模式），不是上游文档的确认。可确认的事实是
> 上表那两组数字——**利润表/现金流量表的该字段整体不可用**。

## 2. 决策（D58–D61）

| # | 决策 | 理由 |
|---|---|---|
| **D58** | **历史 point-in-time 财务数据只以「三表」为来源**；`indicators` 端点**不进入 PIT 数据集**，只用于①当前时点评估（顾问链既有用法）②**抽样口径校验** | 三表带 `report_date_ms`（虽然要修正，见 D59）；`indicators` 的规范化结果里 `disclosed_at=None`、`period_end=None`——**没有任何时点信息**，用它做历史评价就是想怎么滑就怎么滑（`22` §1.3） |
| **D59** | **闸门 = `min(接口披露日, 法定披露截止日) + 1 天`**；两个日期都落库，`available_basis` 写明采信了哪一个 | §1：直接用接口日期会让利润表/现金流量表白等约一年；只用法定截止日又丢掉了"资产负债表 Q1 的 +25 天"这类可信信息。`min` 同时取到"新鲜"与"安全"（披露不可能晚于法定截止日）。**+1 天**是因为披露可能发生在盘中/盘后，日粒度数据无法判别，取最保守读法 |
| **D60** | **落库必须自证 + 可断点续跑**：写库粒度 `(标的, 报表)` 整体替换、台账与内容同进同出、台账记**异常消息**、数据集带版本/范围哈希/窗口/口径 | `14` §6.3 的教训（没台账分不清"没数据"与"没取到"）与 `19` 的教训（口径必须自证）。本轮实测又踩到两条：台账只记异常**类型**导致白查一轮；误按"一次写一个报告期"会让后一次抹掉前一次 |
| **D61** | **F-Score 本地化**：新增本地口径 `roa`（净利润 ÷ **期末**资产总计），`calculate_f_score` **优先本地 `roa`、回退厂商 `total_assets_net_ratio`**；两个口径**不合并成一个键** | 本地口径自证（公式+来源都在自己手里）且带披露日；厂商口径与本地实测相对差 **<1%**（厂商疑似用平均总资产），但**不带披露日**。合并成一个键就等于把两个口径混为一谈 |

## 3. 设计与实现

### 3.1 表结构（`data/market/finsight_market.duckdb`）

| 表 | 用途 | 关键列 |
|---|---|---|
| `financial_facts` | 财务事实（长表，一字段一行） | `thscode, statement, period_key, period_end_ms, field, value, unit, currency, disclosed_at_ms, available_from_ms, available_basis, api_basis, source, run_id, fetched_at` |
| `financial_sync_symbols` | **取数台账**（每个 (标的, 报表) 一行） | `status, periods, fields, gaps, requested_start_ms/end_ms, api_basis, error_code, error_message, run_id, fetched_at` |
| `financial_sync_meta` | **数据集自证** | `version, universe, universe_hash, universe_reasons, window_*, scope, period, gate_rule` |

**长表而不是宽表**：三表的字段集随标的类型变化（银行没有"营业成本"），宽表要么大量 NULL、
要么每加一个字段就要迁移；长表把"缺字段"如实表达为**没有这一行**。

**刻意不动**：被 D9 冻结的 `financial_statements`（131.6 万行、只有年报口径、`evidence_id` 全空）
保持只读——它是**另一份**来源不明的历史快照。新数据集另起三张表，两者不混。

### 3.2 PIT 读取 + **断言而非注释**

`repository.financial_snapshot_asof(thscode, as_of_ms)` 只返回 `available_from_ms <= as_of_ms`
的报告期，并返回**当前期**与**上年同季**（Δ 类信号要用同季同比：中国季报是累计口径，
`api_basis` 记作 `quarterly_cumulative_unknown`，所以"Q3 累计 vs 上年 Q3 累计"才是同一口径）。

返回前逐行自检（P0-4.3 的同一纪律）：

```python
if item["available_from_ms"] > as_of_ms:
    raise ValueError("…返回了闸门之后的财务事实…PIT 闸门被绕过即为未来信息泄漏。")
```

### 3.3 范围（D36：候选池 + 已确认标的，不做全市场）

`scripts/sync_financials.py --universe candidate+confirmed`：

- **候选池** = 最新交易日按 20 日成交额排序**前 200**（与 `13` 号文档的流动性口径同源）；
- **已确认标的** = 业务库 `security_identities`，**按标的代码正则过滤掉指数**
  （实测该表里有 `881166.TI` 军工装备，`asset_type=a-share-index`，指数没有财务报表）；
- 范围与入选理由一起写进 `financial_sync_meta`，并算 **范围哈希**——"这次到底同步了谁"可审计。

### 3.4 幂等与续跑

`--skip-synced` 按台账跳过三表都已取到的标的；写入粒度是 `(标的, 报表)`（接口一次请求返回该报表
全部期数，所以"重新同步 = 整体替换"是正确粒度）。批量并发默认 4，每批之间礼貌间隔 0.2 秒。

### 3.5 用户能自己敲的一条命令

```powershell
.\.venv\Scripts\python.exe scripts\financial_snapshot.py --symbol 600519.SH --as-of 2024-06-30
```

它把三件**必须一起读**的东西摆在一起：可见报告期与闸门（采信了接口日期还是法定截止日）、
原始字段与本地算出的比率（公式一并打印）、F-Score 的逐项判定（**含算不出来的项**）。
`--json` 给脚本吃。

> ⚠️ **运维注意**：同步进程存活期间，DuckDB 文件被该进程持有，只读工具会报
> `另一个程序正在使用此文件`。等同步结束再跑快照命令即可（不是数据问题）。

## 4. F-Score 本地化 与 厂商口径交叉校验

### 4.1 本地能算 7/9

| F-Score 项 | 本地输入 | 本地可算？ |
|---|---|---|
| 资产回报为正 / 改善 | `roa = net_profit / assets_total` | ✅ |
| 经营现金流为正 | `act_cash_flow_net` | ✅ |
| 现金流覆盖利润质量 | `act_cash_flow_net / assets_total` vs `roa` | ✅ |
| 资产负债率下降 | `total_debt / assets_total` | ✅ |
| 销售毛利率改善 | `(operating_income − operating_costs) / operating_income` | ✅（银行没有营业成本 → N/A） |
| 总资产周转改善 | `operating_income / assets_total` | ✅ |
| **流动比率改善** | 需要**流动负债合计**——三表接口的资产负债表只返回 15 个字段，**没有它** | ❌ 如实 N/A |
| **未增发** | 需要股本变动信息，三表不提供 | ❌ 如实 N/A（既有实现即如此） |

### 4.2 交叉校验：本地算的比率 vs 厂商指标

`scripts/sync_financials.py --indicators-check N` 用 `indicators` 端点做对照（**只校验、不落库**）：

| 标的 | 比率 | 本地 | 厂商 | 相对差 |
|---|---|---|---|---|
| `600519.SH` | 资产负债率 | 0.151931 | 0.151931 | **0.00%** |
| `600519.SH` | 销售毛利率 | 0.895552 | 0.895552 | **0.00%** |
| `600519.SH` | ROA | 0.148951 | 0.150218 | 0.84% |
| `600519.SH` | 总资产周转率 | 0.293490 | 0.296000 | 0.85% |
| `000001.SZ`（银行） | 资产负债率 | 0.909067 | 0.909067 | **0.00%** |
| `000001.SZ` | ROA | 0.004262 | 0.004299 | 0.86% |

## 5. 限制与仍未解释（诚实挂着）

1. **违规延迟披露会带来乐观**：按法定截止日开闸的前提是"披露不晚于截止日"。若某公司违规拖延，
   闸门会提前若干天。本地**没有公告日数据**可以校验这一点。
2. **接口日期若早于真实披露日**，`min` 会采信它而略偏乐观。实测资产负债表 Q1 的滞后落在
   15–30 天（看着正常），但**无法证明**它一定不早于真实披露日。
3. **季报是否为累计口径仍未知**：接口的 `period` 字段只是回显请求参数（实测值恒为
   `'quarterly'`），规范化层因此如实标成 `quarterly_cumulative_unknown`。本轮用**同季同比**
   规避（累计 vs 累计），但**没有证实**它一定是累计口径。
4. **`report_date_ms` 异常的上游原因未确认**：§1.3 的"推移到下一个报告周期"是**基于日期模式的
   推断**，没有上游文档支持。
5. **只有 201 只标的**（D36 的收窄范围），且**不含退市标的**（行情库本身不含，`07` §4.1 的
   幸存者偏差在这里同样成立）。
6. **ROA 与总资产周转率的 0.85% 差异**未向上游确认（推断为"平均 vs 期末"）。
