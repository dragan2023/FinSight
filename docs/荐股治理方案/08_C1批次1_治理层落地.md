## 1. 数据模型（schema v32）

| 表 | 作用 | 关键列 |
|---|---|---|
| `hypothesis_registry` | 预注册台账 | `reference`(UNIQUE，形如 `trend_20_60_v1@v2`)、`kind`、`definition_json`、`params_json`、`params_hash`、`submitted_at`、`frozen_at`、`status(draft/frozen/retired)`、`exploratory`、**`trial_count`** |
| `evaluation_batches` | 评估批次 | `plan_json`、`stop_criteria_json`、`status(open/frozen/closed)`、`verdict_json`、`superseded_by` |
| `batch_members` | 批次隔离（多对多） | `(batch_id, artifact_kind, artifact_id)` 主键 |
| `rule_change_log` | 变更留痕 | `field`、`old_hash`、`new_hash`、`reason`、`hypothesis_id`、`replacement_id`、`forced_new_batch_id` |

`trial_count` 这一列是**为多重检验校正留的**：`02` 号文档 §A.2 要求统计"全部尝试过的因子数
（含放弃的）"，而不是最终保留数。批次 3 的扫描一次性占用了 **10,572** 次试验，这个数字
必须记在台账里，否则未来的 C3 判定会低估搜索空间、把噪声当发现。

### 四个触发器（规则的最后一 道防线）

| 触发器 | 拒绝条件 |
|---|---|
| `hypothesis_registry_frozen_update` | `OLD.status='frozen'` 时改写 reference/kind/name/definition/params/params_hash |
| `hypothesis_registry_batch_frozen_update` | 假设所属批次 `status='frozen'` 时改写上述列（方案 02 §4 约束 1） |
| `hypothesis_registry_frozen_delete` | 删除已冻结假设（删除会抹掉评估证据） |
| `evaluation_batches_closed_immutable` | 改写已关闭批次的 name/plan/stop_criteria |

**允许的生命周期变更**（不触发守卫、也不开新批次）：`status`（含 → `retired`）、`frozen_at`、
`notes`、`trial_count`。理由：退役和注释不改变规则本身。

**为什么用触发器而不只靠服务层**：服务层可以被绕过（脚本、手工 SQL、未来的新代码路径）。
触发器让"冻结期改规则"在**数据库层**失败——这正是方案 02 §8 把
「流程负担过重、实际执行时绕过冻结」列为中高风险时要求的"程序拒绝而非提醒"。

## 2. 四条机制落在哪里

### G1 预注册门禁

`backend/app/strategy/service.py` 的 `StrategyService.run()` 第一行：

```python
spec = get_spec(data.strategy_id)
self._governance.assert_runnable(f"{spec.id}@{spec.version}")
```

放在**取数之前**，所以未登记的策略跑不了实验，也不会产生任何外部调用。
拒绝类别：`governance_not_registered`（没登记）/ `governance_not_frozen`（登记了但还在 draft）。

### G2 冻结

`GovernanceService.freeze()` / `retire()` / `amend_definition()`。
`amend_definition()` **只对 draft 生效**；冻结后唯一的合法路径是登记**新的 reference**
（方案 A.1：「登记后不得改名或改定义——变更视为新因子」），否则返回
`governance_rule_frozen` + "变更必须登记为新的 reference"。

### G3 变更即新批次

`GovernanceService.record_change()` → `GovernanceRepository.apply_change()`，
在**同一个 SQLite 事务**内完成：关闭旧批次（`superseded_by` 指向新批次）→ 插入新批次 →
写 `rule_change_log`（带 `forced_new_batch_id`）。

**有意的设计取舍**：新批次**默认继承**旧批次的 `plan_json` 与 `stop_criteria_json`。
这样"改规则"这件事**不可能顺带放松停止条件**——想放松就得在新批次里显式写出来，
而那句显式声明本身就是一条可审计记录（对齐 G8「达标即停，禁止延长或降低标准」）。

### G4 批次隔离

- 建议登记：`AdvisorLedger.register()` 与 `ResearchPredictionLedger.seal()` 都要求
  `batch_id`；没有进行中的批次 → `governance_no_batch`，**拒绝登记**（方案 02 §4 约束 4）。
  建议同时写入 `batch_id` 列与 `batch_members`。
- 统计：`batch_statistics(batch_id)` 只聚合该批次；`combined_statistics()` 默认
  `governance_cross_batch` 409 拒绝，显式确认后仍返回 `usable_for_verdict: false`。

## 5. 本次刻意**没有**做的事

1. **没有让 `batch_statistics` 产出命中率 / Brier / 校准**——那是**批次 5 双轨独立结算**的内容。
   治理层只回答"这个批次里有什么"，不提前产生"结论"。否则治理层会变成第二个（更隐蔽的）
   事后调参入口。
2. **没有修改任何门禁阈值**（D4）。F15 / F23 两条已登记为 draft 提案，等真正改代码时走
   `record_change`，届时当前批次会被自动关闭并开启新批次——**这是设计意图，不是副作用**。
3. **没有给治理层加"方便接口"**：不提供改写已冻结规则、改写已关闭批次、或直接跨批次合并的端点。
   治理的价值就在这些拒绝里。
4. **没有自动开启新的评估批次**（批次之间必须由人或脚本显式动作）。
