# 事件研究加速：预计算面板（85× 提速，结果逐位一致）

> 起因：用户问"每个阶段都要跑一次 pwsh 验证吗？它每次都要下载全市场数据吗？能不能提速？"
> ——我实测后承认：**不下载数据**（全程零网络），但**每轮研究确实要重扫历史**，
> 单字段 52.8 分钟，且同一段历史我重算过三轮。
> 本文档记录加速的做法、**证明结果没变**的证据、实际收益，以及过程中踩的坑。

---

## 1. 一句话结论

| | 加速前（逐日查库） | 加速后（预计算面板） |
|---|---|---|
| 单字段全历史（1013 个评估日） | **3165 秒（52.8 分钟）** | **37 秒** |
| 提速 | — | **85×** |
| 结果 | — | **逐位一致**（`results`/`variants`/`by_period`/`multiplicity` 全等） |
| 网络 | 零 | 零 |

面板构建本身 **6 秒**（一次全表扫描）、**383 MB**、缓存命中 **0.05 秒**；
行情或除权表一变，指纹不一致 → **自动重建**（不会带病使用旧口径）。

## 2. 慢在哪（先量，再改）

原来的实现**每个评估日**跑两次全表查询：

- `cross_section(date_ms)`：0.25–0.44 秒/日
- `settlement_returns(date_ms, 20)`：0.21–0.62 秒/日

1033 个评估日 = **2000+ 次全表扫描**（`daily_k` 1026 万行）。隔离测得的合计是
1.15–1.55 秒/日，而真实长跑是 3.06 秒/日。**这个 2 倍差距我到现在也没完全解释清楚**
（试过：早期日期更贵——不成立，早/中/晚期查询都是 0.1–0.6 秒；内存增长导致 GC 变重——
不成立，实测三种情形速率都平坦）。加速之后它**已不重要**：那条通路只剩"等价比对"用途。

---

## 3. 做法：一次全表扫描，物化所有评估日的输入

新增 `backend/app/market_warehouse/repository.py` 的面板：

- 独立文件 `data/market/finsight_event_panel.duckdb`（**不动行情仓库本身**，目录已在 `.gitignore`）；
- `build_event_panel()`：一条 SQL 用窗口函数把每个 (交易日, 标的) 需要的量算全
  —— `turnover_today` / `turnover_20` / `close_20_ago` / `close_60_ago` / 20 日窗口的
  公司行动合计 / `forward_return`；
- `event_panel_window(dates=[...])`：**按日期分块**读取，只读池内那 1033 天（面板有 2427 天，
  不限定就白读 58% 的行）；
- 版本号 + 行情源指纹（行数、最大日期、除权行数与最大除权日）写进 `event_panel_meta`；
  `event_panel_status()` 一旦发现版本或指纹不一致就判"不可用"，`run_fields` 随即**重建**；
- 事件研究侧 `run_fields(source="panel"|"live")`：**两条通路共用同一个 `_details` 核心**，
  所以"切换前后一致"是可以逐位比对的，而不是靠信任。

## 4. 为了"逐位一致"，实测踩出的三处细节

等价不是自然成立的，下面每一条都是**先不一致、查明原因、再修平**的：

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 1 | 前向收益有 6 处不符 | 公司行动按时间戳区间 `(T, T+20]` 计入，而 57,116 条除权记录里有 **274 条**落在个股 K 线范围内却没有当天的 K 线（休市/停牌）。这批动作的窗口边界与"正好落在 K 线日"的那批**差一格** | 把动作分两股取窗口再相加：正好落在当日用 `1 FOLLOWING .. 20 FOLLOWING`，落在两日之间用 `CURRENT ROW .. 19 FOLLOWING` |
| 2 | 快照列有 27,141 处不符（最大相对差 91%） | 我用绝对容差比"20 个亿元级成交额之和"，2e10 的 1 ULP 就有 4e-6 → **判据本身错了** | 改成相对容差 1e-9；实际相符部分最大相对差 8.8e-16（机器精度） |
| 3 | 仍有 3 处 `turnover_20` 不符（长期停牌复牌股，如 000792 盐湖） | `cross_section` 有 **400 自然日回溯上限**，复牌股的 20 根 K 线跨度可好几年；我的 20 行窗口帧会混进窗口外的行。第一版想用 `max(date_ms) OVER w20` 当阈值——**完全没生效**，因为帧的末行就是当前行，条件恒真 | 用一条**有界**修正语句：只对"20 根 K 线跨度 > 400 天"的稀有行，用关联子查询按同样语义重算 |

**等价性证据（三个层次）**：

1. 真实库抽样 **12 个评估日 / 49,095 个 (日期, 标的) 单元**：快照列 0 处不符、
   前向收益 0 处不符、NULL 0 处不一致、集合差集 0，最大相对差 **8.8e-16**
   ——脚本 `scripts/verify_event_panel.py`，可直接重跑；
2. 真实库小范围：面板与逐日查库的 t 值**逐位相同**（1.7187069140093887）；
3. **全量验收**：同参跑完整历史，`results` / `variants` / `by_period` / `multiplicity`
   全部相等，t 值一字不差。

## 5. 我自己的测量错误（必须记下来）

第一次带 `--profile` 跑面板通路，得到 **973 秒**，我差点据此下结论"只快了 3.25×"。
真相是：**`--profile` 打开了 tracemalloc，它追踪每一次分配**，把 37 秒的跑拖成 973 秒（26×）。
我测的是探针，不是代码。

随后做了决定性实验（`不保留 + GC 开` / `保留 + GC 开` / `保留 + GC 关`，各跑满 1033 个日期）：
**33.3s / 36.0s / 35.7s，速率平坦** → 既排除 GC，也排除"逐日保留撑大内存"这个我当时最怀疑的解释。
不带 profile 重跑：**37 秒**。

教训两条：
1. **别用会拦截分配的 profiling 工具测墙钟**——tracemalloc / 逐行 profiler 都算这一类；
2. 微观隔离测量（3 个日期、40 个日期）**不能外推长跑**：同一条通路在 3 日期上量到 1.15s/日、
   在 1033 日期上是 3.06s/日。要下性能结论，就在**真实规模**上量。

## 6. 顺带发现的一个口径缺陷（**没有顺手改**）

比对时发现 `screener.service.total_return` 与 `_factor_value` 的动量项写成 `(1 + 送股)`，
**漏掉配股比例**；而仓库里 P0-1 验证过的规范式子
（`corporate_action_total_return_history`）是 `(close × (1 + 送股 + 配股) + 分红 − 配股成本) / prev_close`
——**配股在乘数里**，两处 docstring 也都写着包含配股。实测影响面：49,095 个抽样单元里
**6 处**前向收益因此不符（0.012%，全部是窗口内有配股的标的）。

**我没有在加速这一轮里顺手改它**：那样"新旧结果一致"这个验收条件就废了，而且会静默改掉
已经汇报过的 IC 与事件研究数字。面板按**既有**口径实现（`fwd_rights` 仍算出来但不进公式），
缺陷登记为待办：**F47 / D49**（见 §8），修复要走 `record_change` + 重跑 IC 与事件研究。
